## What was completed

### The timetable belongs to the admin

Five writes moved from `requireTeacher` to `requireAdmin`: `createSubject`,
`createClass`, `createCourse`, `enrolStudent`, `withdrawStudent`.

Worth recording that `requireTeacher` rejects ADMIN outright, so before this an
admin could not touch the timetable at all — it was teacher-only, which is the
opposite of the intended rule rather than a weaker version of it.

Two consequences that were not optional:

**`createCourse` no longer defaults the teacher to the caller.** It used to mean
"I teach this", which was right while a teacher built their own timetable. With
admins as the only callers that default resolves to the admin, who cannot teach,
and the request would have failed with a message about the caller's role rather
than about the field that was actually missing. The teacher is now required, and
the message says so.

**Two reads were widened rather than swapped.** `view a class register` and
`view every course` now accept either role. Neither single guard fits:
`requireTeacher` would leave an admin able to enrol a student into a class but
unable to see who is already in it — a good way to add somebody twice — and
`requireAdmin` would take a teacher's own class list away from them. A student is
still refused, which is the part that matters, since a register names every
classmate.

### Every delete now explains itself

| Removing | Refused while |
|---|---|
| Student | they have any recorded mark or any submission |
| Subject | any course still teaches it |
| Class | anyone is enrolled, or any course is taught to it |
| Course | any work has been set for it |

Every foreign key in this schema is already `ON DELETE NO_ACTION`, so the
database refused all of these before today. What it could not do is explain
itself: the refusal arrived as a driver-level constraint violation, which
`GlobalExceptionHandler` can only honestly report as a **500** — a server fault,
for what is a legitimate answer to a reasonable request.

**The check is the message. The constraint is the guarantee.** Removing either
leaves the system correct and worse. Adding `ON DELETE CASCADE` instead would
delete somebody's marks as a side effect of tidying a subject list, which is the
one thing this design has consistently refused to do.

Verified against the running application:

```
'Mathematics' is still taught on at least one course and cannot be deleted.
'Grade 10A' still has students enrolled and cannot be deleted. Withdraw them first.
Work has already been set for General - Unassigned (teacher), so the course cannot be deleted.
'student' has at least one recorded mark and cannot be deleted.
```

### The one distinction inside student deletion

A student's enrolments are deleted with them. Their marks and submissions block
the delete entirely.

An enrolment records **the current arrangement** — where somebody is. A mark or a
submission records **something that happened** — that work was handed in, and that
it was judged. The first can be tidied away without losing anything; the second
cannot be removed as a side effect of an administrative action.

Neither is left to a cascade. The enrolment rows are deleted explicitly, in the
same transaction, because `fk_enrolment_student` does not cascade either and the
delete would otherwise be impossible.

### Account management now matches across roles

| | Teacher | Student |
|---|---|---|
| reset password | existed | **added** |
| edit | **added** | **added** |
| delete | existed | **added** |

The student reset closed a genuine dead end. A password is a one-way hash, so a
student whose temporary password was lost had an account nothing in the system
could make usable again.

Two things an edit deliberately cannot do:

- **Change a username.** It is the generated login id (`STU20260001`) and every
  audit entry names the person by it; editing it would silently detach somebody
  from their own history. `UpdatePersonRequest` has no username field at all —
  omitting it is a stronger guarantee than validating it.
- **Change a password.** Edits got their own DTO rather than reusing
  `PersonRequest`, which carries a `@NotBlank` temporary password. Sharing it
  would have made an admin retype a password to correct a spelling, and would
  have let an edit rotate a credential as a side effect of changing a name.

### Courses have Delete but no Rename

Changing a course's subject, class or teacher is not an edit — it is a different
course, and the work already set against the old one would move with it
silently. Delete and re-create makes that consequence visible, and the delete is
refused while that work exists.

### Both dashboards rebuilt

The same course rows read three ways, grouped in the browser rather than fetched

the first if anything changed between them.

- **Student:** Subjects / Classes / Teachers tiles, a timetable carrying the

## Challenges faced and how they were resolved

### A card gated to a role that never visits its page

**Problem.** Making the timetable admin-only started as one line: change the
card's `*ngIf="isTeacher"` to `*ngIf="isAdmin"` on the dashboard. The backend
suite stayed green and the frontend built clean.

**Resolved.** `AppComponent` sends an admin to `/admin` the moment they sign in,
so an admin never opens the dashboard. The card was therefore visible to nobody —
hidden from teachers by the new rule, and sitting on a page the only permitted
role never visits. Timetable management had been removed from the interface
entirely.

Fixed by extracting it into `/admin/timetable`, behind `adminAuthGuard`, with a
nav entry and a dashboard quick link.

Only driving the browser as each role found this. It is the same lesson the CSRF
defect and the two route-guard defects taught, and it is now three for three:
a green test suite says nothing about which page a user is actually looking at.

### A test failure attributed to the wrong cause

**Problem.** Adding `-XX:+EnableDynamicAgentLoading` to Surefire appeared to break
24 tests, all failing with *"class path resource
[AccountSelfServiceTest.class] cannot be opened because it does not exist"* —
while the file was plainly present on disk.

**Resolved.** The flag was not the cause. That run coincided exactly with the
IDE reporting *"the build file has been changed"*: the Java language server was
rebuilding `target/` while Maven was reading it, and a class file disappeared
from the classpath mid-run. With the identical flag in place the suite is green
twice consecutively with zero warnings.

The flag is also already `true` by default (`-XX:+PrintFlagsFinal` confirms it),
so it changes no behaviour — stating it explicitly suppresses the warning and
marks the spot to revisit when a future JDK flips that default.

Recorded because the mistake was in the reasoning, not the code: the change was
blamed before the assumption was tested. Bisecting it — plugin declared with no
`argLine`, then a benign `argLine`, then the real flag — was what settled it.

### A duplicate check that would have refused every edit

**Problem.** `saveProfile` asks `existsByNationalId` before writing. Reusing it
for edits means saving a record without touching its national id collides with
itself, refusing every edit that leaves the field alone — which is the common
case.

**Resolved.** The edit path asks a different question: *does this id belong to
somebody else?* `findByNationalId` returns the owning row so the caller can
compare it against the record being saved. Both paths still end at
`uq_person_profile_national_id`, which is what actually enforces the rule.

There is a test for exactly this, because the bug only appears when the field is
untouched and would have looked like a working feature in any demonstration that
changed the id.

### A name that cannot be split back apart

**Problem.** `StudentView` and `TeacherView` published `fullName` only. An edit
form needs first, middle and last separately, and recovering them from a joined
string is guesswork — "van der Merwe" has no reliable seam.

**Resolved.** Added the three parts alongside `fullName`. Three strings on a DTO
is a smaller cost than a name-splitting heuristic that is wrong for a real
proportion of the school.

### A verification script that deleted real data

**Problem.** The Playwright regression script's cleanup step located its target as
"the first deletable row on screen" rather than the row it had created. It
removed two legitimate assignment rows across two runs and left its own test rows
behind.

**Resolved.** Scoped the deletion to the row matching the created title. The two
removed rows were duplicates of records that still exist, so nothing unique was
lost, but the failure was mine and is recorded rather than quietly repaired.

A related self-inflicted problem the same day: `spring-boot:run` started in the
background held port 8080 and made a later `mvnw spring-boot:run` fail with
*"Port 8080 was already in use"*. Stopping the parent Maven process is not enough
— it forks a child JVM that outlives it.

## Open items

- **No test covers a stale running backend.** Twice today the application under
  verification was an older build than the source, and the symptom both times was
  a rule appearing not to apply. There is no automated guard against this; the
  check is to restart before verifying.
- **Migrations are still unexercised by the suite** (PRD R10). The new
  constraints rely on V4's foreign keys, which the H2 tests do not run.
  `ddl-auto=validate` remains the only thing catching drift.
- **A course cannot be edited**, only deleted and re-created. Deliberate, but it
  means correcting a typo in who teaches what costs the course's identity.
- **Deleting a teacher and deleting a student use different rules.** A teacher is
  refused while they own a course or an assignment; a student while they have a
  mark or a submission. Both are correct for their role, but the asymmetry is
  worth knowing before assuming one from the other.
- **No bulk delete anywhere**, by design — each refusal is per-record and needs
  reading.

## Where the project stands

The system now records who may change the shape of the school, and refuses to
lose anything as a side effect of an administrative action. Every destructive
operation either succeeds or explains itself in a sentence naming what is in the
way, and that behaviour is asserted in both the test suite and the browser.

The repository name still promises more than the code delivers. There is no
attendance, no terms, and no timetable periods — "timetable" here means which
teacher teaches which subject to which class, not when. Saying so plainly
remains more useful than pretending otherwise.
