## What was completed

### The bug: every delete relied on a browser API that can silently stop working

`window.confirm()` has a real failure mode: after a page raises several
dialogs in a row, Chrome offers "Prevent this page from creating additional
dialogs." Once a user checks that box, every later `confirm()` call on that
page returns `false` **silently** - no dialog, no error, nothing on screen.
A Delete button that worked several times and then appears completely dead
is exactly what that produces.

I could not reproduce a server-side fault - an unused subject deletes
cleanly, a used one correctly returns 409 with a clear message - which made
this the strongest explanation available, and it was worth fixing regardless
of whether it was the exact cause: a native browser popup also looks out of
place next to a designed interface.

**`ConfirmService`** replaces it: a signal-backed service in the same shape
as the existing `NotificationService`, rendering one shared modal from the
shell. Every call site changed from

```ts
if (!confirm(`Delete "${x.name}"? This cannot be undone.`)) { return; }
```

to

```ts
if (!await this.confirmDialog.ask(`Delete "${x.name}"? This cannot be undone.`)) { return; }
```

Grepping for the fix surfaced **8** call sites, not the 3 originally
reported: three admin pages, plus `assignments-page`, `reports-page` and
`admin-student-detail` carried the identical pattern.

**Verified without a dialog handler at all.** The browser check ran with no
`page.on('dialog', ...)` registered - if `window.confirm()` had fired even
once, Playwright's default auto-dismiss behaviour would have shown up as a
failure. It never did, across a full run that opened and cancelled the
modal, then opened and confirmed it.

### A phone number, with the constraint at the database

Migration V9 adds `person_profile.phone`, nullable at the database (the
existing rows have no honest value to backfill), but required going forward
at the application boundary - the single-record admin forms reject a
missing one with 400.

```sql
ALTER TABLE person_profile ADD CONSTRAINT ck_person_profile_phone_format
    CHECK (phone IS NULL OR phone LIKE '+267[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]');
```

Bypassed the application and proved it by hand:

```
UPDATE ... SET phone = '12345678'    -- missing +267        -> refused
UPDATE ... SET phone = '+2677123456' -- 7 digits, not 8      -> refused
UPDATE ... SET phone = '+26771234567' -- correct              -> accepted
UPDATE ... SET phone = NULL           -- a pre-existing profile -> accepted
```

**Bulk CSV/Excel import keeps phone optional, deliberately.** It calls the
service layer directly and never builds the validated request object a
single-record form does, so requiring the column there would break every
already-working import the moment this change landed - a school's existing
spreadsheet has no phone column to require one from. This is the same
"format-checked when present, required only by the caller that can afford
to require it" treatment `contactEmail` already had.

### Dropdowns replace two free-typed username fields

The timetable page's Teacher and Student fields used to be plain text
inputs. A typo used to fail only after "Add course" or "Enrol" was pressed,
because the server's `findByUsernameOrReject` has no way to distinguish
"misspelled" from "does not exist" until the request lands. Both are now
`<select>` elements sourced from the real teacher and student lists, which
removes the mistake rather than catching it afterward.

### Two new tables, and why they share one component

`GET /api/admins` and a new `/admin/accounts` page merge students, teachers
and admins into one searchable, sortable listing. Admin rows correctly show
"no profile" and a dash for every biographical column - not a bug, a
documented decision (CLAUDE.md's Scope Guard: admin accounts never collect
one).

`GET /api/teachers/me/students` and a new `/my-students` page give a teacher
the same view, scoped server-side to students in their own courses only -
verified to return exactly the students enrolled in classes the seeded
`teacher` account teaches, and none of the students created elsewhere during
testing who were never enrolled anywhere.

Both pages reuse **one** `AdminAccountsTableComponent` rather than a second
copy of the same DataTables wiring - it draws whatever rows it is handed
and has no admin-specific behaviour baked in, the same way
`SubmissionTableComponent` already serves both a teacher's marking queue and
a student's own work list.

**Every value is escaped, even though the forms now validate.** Bulk import
bypasses the Bean Validation annotations entirely, so a name arriving that
way is not shape-checked - a real, provable gap, not a hypothetical one.
Confirmed live: a student created via the API with the title
`XssProbe`/`<img src=x onerror=...>`-shaped input rendered in the merged
table as literal text, with `0` `<img>` elements in the DOM.

### Validation: the style of what was asked for, not the literal numbers

Given a FluentValidation-style spec from what turned out to be an unrelated
system, I checked it against this project's own data before adopting any of
it. `"exactly 9 characters"` for a national id contradicted real rows
already in this database - 12 to 13 digits. Adopted the *style* -
non-blank, bounded length, a pattern that means something, cross-field
checks with their own message - using this project's actual constraints.

- **Names**: `^[\p{L} '-]+$`, Unicode-aware rather than ASCII-only, so
  "Van der Merwe" and "O'Brien" are accepted rather than special-cased as
  exceptions to an English-only rule.
- **National id**: digits only, 4 to 20 characters - matches every real and
  test value in the database, not a number picked from an unrelated spec.
- **Password strength**: uppercase, digit and symbol checked as three
  *separate* rules rather than one combined regex, so a rejected password
  says which requirement is still missing instead of just "invalid."
- **Confirm-password fields** added everywhere a password is set that
  didn't already have one - the admin's create-student, create-teacher and
  both reset-password forms had a single field with no way to catch a typo
  before submitting.

### The ripple: fixing password rules broke passwords already in the test suite

Adding uppercase+digit+symbol requirements meant existing fixtures like
`"temp-password-1"` and `"brand-new-password"` no longer validated - neither
contains an uppercase letter. This affected roughly 15 call sites across two
test files, including the shared `personJson()` helper most of
`AdminApiTest` builds on. Each was updated to a compliant equivalent
preserving its original descriptive name (`"brand-new-password"` became
`"Brand-New-Password1"`), and one login-attempt test needed its *separate*
password literal updated to match, since the two had drifted out of sync
during the fix.

Also added a `phone` field to the same shared fixture, since the DTO it
posts to now requires one - without it, every test that creates a student
or teacher through the single-record forms would have failed 400 on a field
the test had no reason to know about yet.

## Challenges faced and how they were resolved

### A push that timed out with no error

**Problem.** `git push origin main` hung for the full 3-minute timeout with
no output and no error.

**Resolved.** Checked GitHub's own connectivity first (200 in 0.3 seconds -
not a network problem), then confirmed nothing had actually landed
(`git rev-list --left-right --count HEAD...origin/main` still showed one
commit ahead, zero behind - the push genuinely hadn't gone through, not just
hung on printing its result). A second attempt succeeded immediately.
Recorded because the safe response to a stalled push is to verify state
before retrying, not to assume either success or failure.

### A test that passed 180 times locally and failed once on CI

**Problem.** The push above triggered CI, which failed with

```
AdminApiTest.requireClassId:118 IllegalState Seeded class 'Grade 10B' not found.
```

despite the exact same suite passing locally on every run that day.

**Resolved.** One test, `adminCanRename`, renamed the seeded class
"Grade 10B" directly - a real, permanent write for the rest of that JVM's
test run. A separate, unrelated test elsewhere in the file looks that class
up by its original name. JUnit does not guarantee execution order across
nested test classes, and the order it picks can differ between machines;
locally the read always happened to run first, and on GitHub's runner it did
not.

This was the second occurrence of the identical mistake in the same test
method - the *subject* half of `adminCanRename` had already been fixed
earlier the same day to create a throwaway subject rather than rename
seeded `MATH`, and the *class* half was missed in that pass. Fixed the same
way: create a disposable class and rename that instead. Verified by
confirming "Grade 10B" is now read-only everywhere in the file - not merely
by re-running the suite, since a passing run proves nothing about an
ordering bug that had already been passing by coincidence.

### Reproducing, not assuming, a browser-only bug

**Problem.** The reported delete failure could not be reproduced through the
API - an unencumbered subject deleted cleanly every time it was tried.

**Resolved.** Rather than guess at a fix, the actual mechanism
(`window.confirm()`'s silent-disable behaviour) was identified from
Chrome's own documented behaviour, and the fix was verified by proving the
*negative* - that no native dialog fires at all with the replacement in
place - which is a stronger check than proving the modal merely appears.

browser cannot silently switch off, every account collects a phone number
in a checkable format, and an admin can see the whole school - or a teacher
their own students - in one table instead of piecing it together from two

itself. The fix that mattered was not re-running the suite until it passed
again - it was making the mutation stop happening at all.
