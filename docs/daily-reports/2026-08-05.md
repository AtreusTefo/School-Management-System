## What was completed

### The one rule this table exists to enforce

A score cannot exceed the maximum it was marked out of. `ck_assessment_score_within_max`.

"34 out of 20" is not a high mark — it is a corrupt row, and every average
computed from it afterwards is silently wrong while looking entirely normal. That
is why it is a constraint rather than a validation message: the message is a
courtesy, the constraint is the guarantee.

### Nothing derived is stored

| Stored | Derived on read |
|---|---|
| `score`, `max_score`, `name`, who recorded it, when | percentage, subject total, subject percentage, performance level |

A stored average is wrong the moment one mark is corrected, and keeping it honest
needs either a trigger or a job somebody eventually forgets to run. Computing it
means a correction corrects the whole report, with nothing to recalculate.

The same reasoning already governs `overdue` on a submission. It is becoming the
house rule: **if it can be computed from what is stored, do not store it.**

### The arithmetic decision that matters

A subject percentage is **total score over total maximum**, never the mean of the
individual percentages.

A student scoring 5/10 and 90/100 has 95 out of 110 = **86.36%**. Averaging the
two percentages gives (50 + 90) / 2 = **70%**, which silently treats a ten-mark
quiz as equal in weight to a hundred-mark exam.

Both numbers look plausible on a report, sort correctly and export cleanly. Only
one is right. It has a test in the suite and a second one in the browser, and the
seed data deliberately uses those exact marks so anyone changing the calculation
sees the difference immediately.

### Mark ownership, enforced by the schema

A mark can optionally point at the submission it marks. Making sure it points at
the *right* student's submission reuses the composite-key technique from Sprint 4:

```sql
ALTER TABLE submission ADD CONSTRAINT uq_submission_id_student UNIQUE (id, student_id);

CONSTRAINT fk_assessment_submission
    FOREIGN KEY (submission_id, student_id) REFERENCES submission (id, student_id)
```

A mark naming submission 7 and student 3 is only storable if submission 7 really
is student 3's work. When `submission_id` is NULL the constraint does not apply,
which is correct — a test that was never uploaded has no submission to belong to.

## Challenges faced and how they were resolved

### A form whose Save button could never be enabled

**Problem.** Entering a mark in the browser left "Record mark" permanently
disabled, with nothing on screen explaining why.

**Resolved.** The score fields were `<input type="number">` bound with
`[(ngModel)]`. Angular binds a number input through `NumberValueAccessor`, which
writes a JavaScript **number** into a field declared as a string — so
`markScore.trim()` threw, the getter behind the button's `[disabled]` died, and
the button stayed dead.

Changed to `type="text"` with `inputmode="decimal"`. That is also what the strings
were for in the first place: a number input routes the value through a double,
which is exactly how 34.5 becomes 34.499999999999996 on its way to a `DECIMAL`
column. The `type="number"` had been quietly defeating the precision decision it
sat next to.

No API test could have found this. It is a data-binding behaviour, and it needed a
browser.

### Every hand-written write to the new table was refused

**Problem.** The integrity sweep failed entirely, with error 1934 on the first
statement: *"INSERT failed because the following SET options have incorrect
settings: 'QUOTED_IDENTIFIER'."*

**Resolved.** The table carries a **filtered** unique index, and SQL Server
refuses any INSERT, UPDATE or DELETE on such a table unless `QUOTED_IDENTIFIER` is
ON. `sqlcmd` defaults it OFF. The application was never affected — the JDBC driver
sets it on connect, which is why the seed had already written six marks
successfully.

Worth recording because the error looks exactly like the schema rejecting the
data, when it is really the session being misconfigured.

### A UNIQUE constraint that would have allowed one row

**Problem.** "At most one mark per submission" is a plain uniqueness rule, and the
obvious `UNIQUE (submission_id)` is wrong.

**Resolved.** SQL Server treats NULLs as equal for uniqueness, so that constraint
would have permitted exactly **one** assessment with no submission in the entire
table — refusing every test and exam after the first. A filtered index,
`WHERE submission_id IS NOT NULL`, applies the rule only to the rows it concerns.
Caught before writing it, by thinking about NULL semantics rather than after.

### A PDF library that quadrupled the application

**Problem.** Adding `pdfmake` for the export took the initial bundle from 443 kB
to **2.41 MB** and failed the build's budget.

**Resolved.** Nearly all of it is embedded fonts. A static import means every
student who signs in to check their marks downloads a PDF generator they may never
open. Replaced with a dynamic `import()` on first click of Export PDF: the initial
bundle went back to **519 kB**, and pdfmake became two lazy chunks fetched once and
cached.

The button reports a failure if the chunk cannot be fetched, rather than doing
nothing — a button that silently does nothing is worse than one that says why.

### Two browser assertions that were wrong about a correct application

**Problem.** "A student sees their own marks — 0 rows", and a timeout waiting for
a `<select>` option to become visible.

**Resolved.** The first counted rows before DataTables had drawn them; the next
assertion in the same run read the same table's text successfully, which is what
gave it away. The second was waiting for `visible`, and an `<option>` inside a
closed `<select>` is never visible to Playwright — `state: 'attached'` is the
right condition. Both were test defects; the register had loaded correctly in
both cases.

## Second session — input validation, page split, server-side Excel export

### What was done

**EPIC: friendly login errors.** Wrong credentials already returned 401, not the
400 the epic's task literally asked for — kept deliberately, since 401 is the
semantically correct status and an identical message for a wrong username versus
a wrong password is what prevents account enumeration. Angular now shows that
message inline on the login form instead of routing it through the generic error
banner, which used to say "your session has ended" for a login that had never
succeeded in the first place.

**FEAT: centralized input validation.** Three files now own it everywhere:
`validation.ts` (every length/format constant, mirrored from the actual backend
`@Size`/column bound, plus `checkDecimal()` and `fieldErrorMessage()`),
`decimal-validator.directive.ts` (`appDecimal`/`appDecimalPositive` checked
against DECIMAL(6,2)'s real shape), and `field-error.component.ts` (the one place
an inline error is drawn). Jakarta Bean Validation backs every DTO on the server
side, so a request that bypasses the browser is still refused with the same
structured 400 body. Found and fixed a real defect during this work: several
fields were bound with `[attr.maxlength]` instead of `[maxlength]` — the two look
interchangeable and are not, since only the property-binding form activates
Angular's own `MaxLengthValidator` directive. A too-short password had been
reporting itself valid at any length.

**Page split.** What was one long page is now four routed pages — "Work I have
set", "Marking queue", "Performance & marks" (Reports), and a Dashboard — behind
`authGuard` and `teacherGuard`, with `SessionService` and `NotificationService`
extracted so identity and the error banner survive a navigation instead of
belonging to one component. Performance-by-student and the mark book now live on
one Reports page and share a technology (DataTables) and an export story, which
is what the request "these should basically be the same table so a report can be
exported" was actually asking for.

**Server-side Excel export.** `AssessmentReportService` (Apache POI 5.3.0) builds
a two-sheet workbook — Performance Summary, then Marks — by calling the exact same
`AssessmentService` methods the JSON endpoints call, so the download can never
contain a row its caller could not already see, and is never limited to whatever
happened to be paginated in the browser. Exposed at `GET /api/assessments/report.xlsx`.
Percentages are stored as a fraction of 1 with a `"0.00%"` cell format, not as the
literal number — an easy place to get an Excel export subtly wrong.

### Two real defects, both found by driving the browser rather than by reasoning about the code

**An infinite redirect loop.** Every guard's failure path sends the visitor to
`/`. The root route itself carried `authGuard` too, so a signed-out visitor
hitting any guarded page bounced to `/`, re-triggered the same guard, and bounced
again — forever. `curl` proved the dev server answered `/reports` correctly and
quickly, which is what ruled out a server-side cause and pointed at the client
router instead. Fixed by removing the guard from `''`: `AppComponent`'s own
template already hides `<router-outlet>` behind `*ngIf="user"`, so the route
needs no guard of its own — there is nowhere for the router to project a
component into while signed out, guard or not.

**Guards racing session initialization.** `authGuard` and `teacherGuard` read
`SessionService.user()`/`isTeacher` synchronously, on the reasoning that "the
whole app already waits for `checkingSession` before rendering, so state has
settled by the time a route activates." True for a link clicked inside the
already-running app; false for a hard navigation — typing a URL, following a
bookmark, or Playwright's `page.goto()` all start the router's initial
navigation at the same moment `SessionService.init()` fires its first HTTP
call, and the guard was reading `user()` before that call answered. A signed-in
student navigating straight to a teacher-only URL landed on `/` instead of the
expected `/marking-queue`. Fixed by having both guards wait on
`toObservable(session.checkingSession)` until it settles before deciding,
rather than reading the signal on the spot.

Also worth recording: the backend process running throughout most of this
session's manual verification (`mvnw spring-boot:run`, started before this
session began) predated every backend change made in it, including the new
`/report.xlsx` endpoint entirely — this project's stack has no hot reload
(no devtools dependency), so a 405 from a route that plainly exists in the
source is the actual symptom of a stale running jar, not a routing defect.
Restarting it against the current code is what turned that 405 into a 200.
