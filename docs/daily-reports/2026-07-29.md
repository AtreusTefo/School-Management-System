## What was completed

### Independent deployment (`5fdf8ba`)

The backend had the frontend's address written into a Java annotation, and the
frontend had the backend's address written into a TypeScript file. Moving either
one meant recompiling both.

| Half | Address now comes from | Change without rebuilding? |
|---|---|---|
| Backend | `app.cors.allowed-origins` setting | Yes — a launch flag or environment variable |
| Frontend | `src/environments/` | Yes — the production build uses a relative address |

Both are now configuration rather than code.

### EPIC-05: Persistence

Moved from H2 in-memory to SQL Server 2019 (`MSSQLSERVER01`, port 14333).

Schema changes go through **Flyway migrations**, which are numbered SQL files kept
in the repository. Hibernate runs with `ddl-auto=validate` — it checks the tables
match the code and refuses to start if they do not, but it is never allowed to
change the schema itself. The structure has a version and a history instead of
being whatever the tool inferred last time.

### EPIC-06: Accounts and Roles

Two accounts, `teacher` and `student`. Passwords are hashed with BCrypt, never
stored as readable text.

| Role | Can see | Can do |
|---|---|---|
| Teacher | All assignments | Create, edit, delete, reopen, submit |
| Student | Only their own | Submit |

The rules are enforced in the service layer, not hidden in the interface. Hiding
a button is decoration; refusing the request is access control.

One deliberate detail: asking for someone else's assignment returns **404, not
403**. Answering "forbidden" would confirm the record exists, letting an outsider
map the data by guessing id numbers.

### EPIC-07: Assignment Lifecycle

- Edit the title and due date
- Delete, but not while submitted — it must be reopened first
- Reopen submitted work (teachers only)
- Due dates, with `OVERDUE` shown for anything past its deadline

### Data integrity, proven rather than claimed

Every rule below was tested by writing bad data **directly through `sqlcmd`**,
bypassing the application. A rule enforced only in Java is a promise that holds
while everyone goes through your code; a rule in the database is a fact.

| Attempted | Result |
|---|---|
| Assignment owned by a non-existent user | Refused — foreign key |
| Assignment with no owner | Refused — NOT NULL |
| Deleting an account that still owns work | Refused — no cascade, deliberately |
| Duplicate username | Refused — unique constraint |
| Invalid status value | Refused — CHECK constraint |
| 300-character title | Refused, not silently truncated |

Consistency was measured, not assumed: **15 simultaneous submissions, exactly 1
accepted**, every round, through the full security stack.

## Challenges faced and how they were resolved

### SQL Server was running but Java could not connect

**Problem.** `sqlcmd` connected fine while Java could not — which looks impossible.

**Resolved.** Only "Shared Memory" was enabled, and Java's database driver cannot
use it at all. Enabled TCP and pinned port 14333. The pinning matters: this type
of SQL Server instance otherwise picks a different port on every restart, which
would break the connection each time.

### A migration failed on a column it had just created

**Problem.** SQL error 207, "Invalid column name `owner_id`" — in the same script
that created it.

**Resolved.** SQL Server compiles an entire batch before running any of it, so it
checked for the column before the line creating it had run. Split the script into
separate `GO` batches.

### Login worked in every test but failed in a real browser

**Problem.** All API tests passed. Chrome refused every write with 403.

**Resolved.** Two separate causes. Spring Security 6 creates its CSRF token lazily,
so an endpoint that never reads it sends no cookie — fixed by reading the token
inside the endpoint. Then Angular, by design, refuses to attach that token to a
different address than the page came from, which is exactly the development setup.
Fixed with a small interceptor that forwards it to the one trusted address.

No API test could have caught this. Only opening a browser did.

### A test that passed for the wrong reason

**Problem.** The check "a request without a security token is rejected" was
passing. It was testing nothing.

**Resolved.** PowerShell's `-WebSession` remembers headers between requests, so a
token set once was being silently resent forever. Clearing the session made the
test real. A passing test that verifies nothing is more dangerous than a failing
one, because it buys false confidence.

### A browser test that reported a bug that did not exist

**Problem.** The delete test showed 9 assignments before and 9 after.

**Resolved.** Playwright dismisses confirmation dialogs by default, and the
handler was registered after navigation, so the confirm returned false and the
delete never ran. The application was correct all along. Handlers must be
registered before navigating.

### Three design faults found by testing, not by planning

1. **The student account could see nothing.** Assignments defaulted to whoever
   created them, and only teachers create — so the student role was decorative.
   Creating now accepts an optional `assignTo`.
2. **A teacher could not fix their own typo.** Editing was owner-based, so handing
   work to a student surrendered the ability to correct it, while the student
   could rewrite it freely. Editing now follows the **role**, not the row.
3. **A database guarantee nearly disappeared in the move.** H2 had a native `ENUM`
   column type; SQL Server has none, so `status` would have quietly accepted any
   text. Rewritten as an explicit `CHECK` constraint. When changing database,
   re-verify every constraint rather than assuming it travelled.

## Open items

- **The migrations themselves are untested.** The suite runs on H2, so the SQL
  Server scripts are never exercised. `ddl-auto=validate` catches drift, but the
  scripts are unproven (`docs/project/PRD.md` L10, R10).
- **Browser behaviour still needs a browser.** That is how the CSRF fault was
  found, and no API test would have replaced it.
- **No continuous integration.** The 36 tests must be run deliberately; nothing
  stops a broken change reaching `main` (`docs/project/PRD.md` R9).
- **No frontend unit tests.** The Angular half is verified by type-check, build
  and manual browser use only.
- **Duplicate rows from repeated probes** have accumulated in the development
  database. Harmless, but worth clearing.

## Where the project stands

All 8 epics are Done. The system does one thing honestly: it tracks assignment
submission for two roles, with 10 endpoints and two kinds of record.

It has no grades, attendance, timetables, classes or subjects. The repository name
promises a broader system than the code delivers, and the remaining candidates —
classes and terms, account self-service, continuous integration — are listed in
`docs/project/PRD.md` section 7 as **proposed, not agreed**.
