## What I did today

Two pieces of work, in this order: an integrity pass over the delete paths,
which found a real defect; then the admin relationship views that were asked
for — being able to see which subjects and students a teacher teaches, and
which class a student is in with which teachers reach them.

The integrity pass came first deliberately. The new views are read-only, so
they could not have found the delete defect; and the delete defect was in
exactly the tables the new views read from.

### 1. Three delete paths let the database do the refusing

The project's own standard is that a delete which cannot proceed is refused by
the service, with a message naming the obstacle — the database constraint is
the guarantee, but the check is what produces a sentence a person can act on.
Three paths had drifted from that:

- **`SchoolService.deleteCourse`** — a course still used by a timetable slot
  was deleted straight into the foreign key.
- **`SchoolService.unassignTeacherFromStudent`** — the same `courses.delete`
  call, reached by a second route. Fixing only the first would have left this
  one broken, which is why both call sites now go through the same guard.
- **`TimetableService.unschedule`** — a lesson with an attendance register
  taken against it could be removed from the timetable. This is the one of the
  three that destroys evidence rather than merely failing untidily: a register
  records who was actually in a room on a date, and the lesson's removal is not
  a reason for that to stop being true.

Each now checks before deleting and throws with the obstacle named.

### 2. A blocked delete answered 400, not 409

`GlobalExceptionHandler` mapped every `DataIntegrityViolationException` to
`400 Bad Request` with "The record could not be saved because it violates a
data constraint." On a DELETE that is wrong twice over: the status says the
caller sent something malformed when they sent a perfectly good id, and the
message talks about saving a record when nothing was being saved.

The handler now discriminates on the HTTP method — `DELETE` yields `409
Conflict` and "This cannot be deleted because another record still refers to
it." Everything else keeps the 400. This is a safety net behind the service
checks above, not a replacement for them: the service still answers first and
with a better message, and this only catches a path nobody has guarded yet.

### 3. V17 — the index the register was missing

`attendance.recorded_by_id` is a foreign key with no index. V14 created three
indexes for the three ways a register is *read*; this is the fourth case, which
is not a read at all. Every delete of a teacher account has to ask "does any
attendance row still point at this person", and without an index that question
is a full scan of the largest table in the schema — one row per student per
lesson per day.

The migration's header records what is still deliberately *not* indexed
(`attendance.class_id`, the `*_role` columns) so the omission reads as a
decision rather than an oversight.

### 4. Admin can now see both ends of the teaching relationship

Two endpoints, both admin-only:

- `GET /api/teachers/{id}/courses` — the subjects and classes a teacher covers
- `GET /api/teachers/{id}/students` — everybody in those classes, once each

Everything they return is **derived, not stored**. A teacher's subjects are not
a column anywhere; they are the `Course` rows, read one way, and their students
are the `Enrolment` rows of those courses' classes, read another. Storing
either as a list would be a second copy of a fact the timetable already owns,
and the two would disagree the first time a course changed.

`listMyStudents` (a teacher's own roll) and `listStudentsOfTeacher` (an admin
looking at somebody else's) now share one private derivation, so the two
answers cannot drift apart. They differ only in who is allowed to ask and whose
id is used.

On the front end:

- **`/admin/teachers/:id`** is new — subject and class counts, courses grouped
  by class, and the students reached, each linking through to their own page.
- **`/admin/students/:id`** already showed a student's class and teachers; it
  gained a summary row and, more usefully, made each teacher a link, so the two
  pages are now two directions of one relationship rather than two dead ends.
- `CourseView` gained `teacherId` — the student page displayed a teacher's
  username but had no id to link with.

## Challenges faced and how they were resolved

### A delete defect that had to be proved before it could be fixed

The three delete paths were found by reading, and reading is not evidence. The
intent was to drive the API from a browser and watch the response, but with the
frontend not running, `page.goto()` at an API URL produced
`chrome-error://chromewebdata` rather than a response to inspect — Playwright
navigates to pages, and a JSON endpoint returning 409 is not a page.

Resolved by dropping the browser for that one job and writing the probe as
plain Node `fetch` with a hand-rolled cookie jar, which talks to the API
directly and reads status codes. It reproduced the 400 exactly as suspected,
and the same script confirmed the 409 afterwards. The lesson is narrow but
worth keeping: use the browser for what only a browser can answer, and speak
HTTP directly for everything else.

### A test that passed for the wrong reason

`timetabledCourseCannotBeDeleted` passed on its first run, which was suspicious
given it was written to catch a bug that had just been fixed. Reading the
failure message it *would* have produced showed why: the helper picked a seeded
course that already had assignments set against it, so the assignment guard
fired first and the test never exercised the timetable guard at all. It would
have kept passing with the new code deleted.

Resolved by adding `givenFreshCourse`, which creates a subject, a class and a
course of its own so exactly one refusal reason can apply. A green test that
cannot fail for the reason it was written is worse than no test, because it
converts an untested path into an apparently tested one.

### A verification script that hung, then lied

The new browser suite crashed in its own sign-out helper: the element resolved
in the DOM but was not visible. The cause was the script, not the app — the
avatar menu is replaced by a hamburger below 1280px, and the script had just
switched to a 390px viewport for the responsiveness check. Resolved by giving
the helper the same hamburger-aware branch the navigation suite already had.

The second run then reported two failures — no subjects, no students. Also the
script's fault, and a more interesting one: it opened the first teacher in the
list, who is an onboarded account with no courses yet, so the page correctly
rendered its empty state and the assertions read that as missing data. Resolved
by probing the API for a teacher who actually teaches something and testing
against them, and separately asserting that the empty teacher still renders an
empty state rather than an error. Both cases are real; only one of them can
prove that subjects and students display.

### A gap in my own audit that turned out not to exist

Part of the integrity pass was checking which entities carry `@Version`. A
search reported that `AppUser` and `PersonProfile` did not, which would have
been a real gap. They do — the search pattern missed the fully-qualified
`@jakarta.persistence.Version` form. Reported as no gap rather than "fixed",
since nothing needed fixing. `AuditLog` genuinely has none, correctly: an
append-only log has no update to lose.

### Documentation that had drifted further than expected

`CLAUDE.md`'s repository tree was missing 21 frontend files and four backend
ones — every public page, the theme and confirm services, the timetable and
attendance pages, three test classes, and migrations V16 and V17. None of it
described anything false, which is why it had gone unnoticed; it was simply
incomplete enough that the tree was no longer usable as a map. Brought back in
line, along with the test count.
