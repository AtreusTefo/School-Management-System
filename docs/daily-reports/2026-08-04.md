## What I did today

Two pieces of work that turned out to be one. Seven new requirements arrived, and none
of them were features that could be added to the existing schema — they were all
statements about **relationships** the data model could not express. So the day was a
data-model change first and a feature delivery second.

- **Split `Assignment` into `Assignment` + `Submission`**, which is what made a
  class-wide assignment possible at all.
- **Added subjects, classes, enrolment and courses** — one `Course` table answers four
  of the requirements at once.
- **Added PDF upload, hand-in and download**, stored in the database rather than on
  disk.
- **Made role rules facts about the data**, using composite foreign keys, rather than
  checks in Java.
- **Rewrote the Angular frontend** around the new model.
- **Grew the test suite from 48 to 69** and verified the rest by hand.

## What was completed

### The requirements, and where each one lives

| Requirement | Carried by |
|---|---|
| A student is taught by more than one teacher | `Course` rows attached to their class |
| A student is taught more than one subject | the same rows |
| A teacher takes more than one class | the same rows, grouped by teacher |
| A teacher takes more than one subject | the same rows |
| A teacher sets work for a whole class | `Assignment` fans out to one `Submission` per enrolled student |
| A teacher sets work for several classes at once | one request, several courses, one assignment each |
| A student uploads a PDF and hands it in | `SubmissionFile`, then `submission.status` |
| A teacher downloads the PDF to mark it | the same row, scoped to teachers of that course |

Not one of those needed its own column or flag. When a set of requirements collapses
like that, the model has usually found the right shape.

### The central split

`Assignment` used to mean two things at once: the work a teacher set, and one
student's progress on it. It carried both a `status` and an `owner_id`, so every
assignment belonged to exactly one person. Thirty students meant thirty rows with the
same title, and nothing in the schema said they were the same piece of work.

| Table | Means | Rows |
|---|---|---|
| `assignment` | what was set | one, however many students receive it |
| `submission` | one student's state, and their PDF | one per enrolled student |

The signal that this was right: **`status` never made sense on `assignment`.** "Is
this submitted?" has no single answer for a class of thirty, and the old model was
quietly answering it for a class of one.

### Making the role rules true rather than checked

The obvious way to enforce "only a student can be enrolled" is an `if` in the service.
That is policy — it holds while every writer goes through this code. The schema does
better:

```sql
ALTER TABLE app_user ADD CONSTRAINT uq_app_user_id_role UNIQUE (id, role);

CONSTRAINT ck_enrolment_student_role CHECK (student_role = 'STUDENT'),
CONSTRAINT fk_enrolment_student
    FOREIGN KEY (student_id, student_role) REFERENCES app_user (id, role)
```

Neither half is sufficient alone. The `CHECK` would let a row claim `STUDENT` for a
teacher's id; the foreign key would let it claim any role. Together, the only value
satisfying both is that user's real role.

An unplanned consequence worth stating: **a user's role can no longer be changed while
any row depends on it.** Promoting an enrolled student to teacher is refused. That is
the constraint working, not an obstacle — the alternative is a "teacher" still sitting
on a class register as a pupil.

### Why the PDFs live in the database

A file on disk with a row pointing at it is two writes to two systems. Making them
atomic takes real effort that is usually not made, and every failure in between
produces something wrong: a row naming a file that was never written, a file nobody
has a row for, or bytes left behind by a rolled-back transaction.

Inside the database the upload is part of the same transaction as everything else. The
cost is honest and recorded as PRD **L11**: a larger database and slower backups.
Correct at 10 MB per assignment; wrong at video scale.

Three separate checks guard an upload, and they are not redundant — they protect
different things:

| Check | Protects | Where |
|---|---|---|
| `max-file-size=10MB` | the server's memory, before the bytes arrive | container |
| magic number `%PDF-` | against a renamed executable | service |
| `ck_submission_file_pdf`, `ck_submission_file_size` | the data, for every writer | schema |

The middle one matters most. A declared content type is client-supplied: renaming
`malware.exe` to `essay.pdf` sets it to `application/pdf` without changing a byte.

## Challenges faced and how they were resolved

### The schema and the entities disagreed, and startup refused to proceed

**Problem.** Migration V4 applied cleanly, then the application would not start:

```
Schema-validation: wrong column type encountered in column [submitted_at]
in table [submission]; found [datetime2], but expecting [datetimeoffset(6)]
```

**Resolved.** Hibernate maps `java.time.Instant` to `DATETIMEOFFSET`, not `DATETIME2`
— an `Instant` is a moment with a known offset from UTC, while `DATETIME2` is a
wall-clock reading with no offset at all. Added `V5__timestamp_columns_with_offset.sql`.

This is `ddl-auto=validate` earning its place. The mismatch would otherwise have
surfaced as times that silently lost their offset — invisible until somebody in
another time zone disputed whether work was handed in before midnight.

**V4 was left alone deliberately.** It had already been applied and recorded, and
Flyway stores a checksum of every migration precisely so an applied one cannot be
edited underneath a database that has run it. A correction gets its own version, even
when the mistake is twenty minutes old.

### A build that reported success without compiling anything

**Problem.** After changing roughly thirty files, `mvnw compile` reported
`BUILD SUCCESS`. It had actually compiled nothing: `Nothing to compile - all classes
are up to date`.

**Resolved.** Maven's incremental check was stale. `clean` first, then trust the
result. Worth recording because the failure mode is a *passing* build — the same shape
as the false-passing test found in an earlier sprint, and just as misleading.

### A browser test that hung on a button that was correctly disabled

**Problem.** The Playwright driver timed out waiting for a file-chooser dialog that
never opened.

**Resolved.** It was clicking the first Upload button on the page, and on a second run
against the same database that row's work had already been handed in — so the button
was **disabled on purpose**, because the document being marked must not change
afterwards. The selector now takes the first `:not([disabled])` button.

The test tripping over the rule was the rule working. The tempting fix — relax the
assertion — would have hidden it.

### A browser assertion that failed for an honest reason

**Problem.** "Student is taught 3 subjects" failed, reporting 4.

**Resolved.** The fourth is `General`, the holding subject migration V4 created so that
assignments predating the timetable had a course to point at. Deleting those rows would
have been easier and would have thrown away real data. The assertion was wrong, not the
application — the requirement is "more than one", so that is what it now checks.

### A JsonPath expression that compiled and lied

**Problem.** Nine API tests failed with `JSONArray cannot be cast to Integer`.

**Resolved.** A JsonPath **filter** always evaluates to a list, even when exactly one
thing matches. Writing `$[?(...)].id[0]` looks like indexing and is not — it returns
the array. Reading the list and indexing it in Java fixes it, and the helper now says
so, because the failure surfaces some distance from its cause.

## Open items

- **The migrations are still not exercised by the suite** (PRD R10). Tests run on H2;
  V4 and V5 are SQL Server dialect. `ddl-auto=validate` catches drift, and it did.
- **The H2 schema is weaker than production.** JPA cannot express a composite foreign
  key whose second column is pinned to a literal, so tests get the `CHECK` plus a
  single-column key. That still refuses a row claiming a role it may not hold; what
  only SQL Server refuses is a row claiming `STUDENT` for a *teacher's* id. Verified
  by hand (PRD L10).
- **Students enrolled after work is set do not receive it** (PRD R12). Deliberate —
  silently handing a new arrival three weeks of missed deadlines would be worse — but
  it is a gap, not a finished decision.
- **No marks are recorded** (PRD R14). A teacher can download a PDF to mark it; the
  system stores no result.
- **No frontend unit tests** (PRD R13).
- **Terms do not exist** (PRD R11).
- **The PDF check is a magic-number check, not a virus scan** (PRD L12).

## Where the project stands

Fifteen epics, 163 of 171 story points delivered. The system now models a small school
honestly: subjects taught to classes by teachers, students enrolled in those classes,
work set once and received by everyone in the register, and handed in as a document
somebody can actually open.

It still has no grades, no attendance and no timetable periods. The repository name
continues to promise more than the code delivers, and knowing exactly where that edge
sits is what makes the next decision easy rather than fraught.
