## What was completed

### Data integrity and consistency

| Change | Effect |
|---|---|
| `AssignmentStatus` enum, stored by name | `setStatus("banana")` no longer compiles; the column rejects anything outside the two valid values |
| `title` `NOT NULL`, `length = 200` | A null or over-long title is impossible at the storage layer |
| `@Transactional` on the service | One business operation is now one transaction |
| `@Version` column | A competing update is detected and refused rather than silently overwriting |
| `ddl-auto` `update` to `create-drop` | The schema can no longer drift more permissive than the entities claim |
| `open-in-view` disabled | The persistence context closes when the service returns |

The generated schema is now:

```sql
create table assignment (
  id      bigint generated by default as identity,
  version bigint,
  title   varchar(200) not null,
  status  enum ('IN_PROGRESS','SUBMITTED') not null,
  primary key (id)
)
```

### The concurrency defect

The rule "an assignment cannot be submitted twice" did not hold when requests
arrived together. `submitAssignment` read, checked, then wrote, and without a
surrounding transaction each repository call committed separately, so concurrent
callers all passed the check before any of them wrote.

| Build | 15 simultaneous submissions, 5 rounds |
|---|---|
| Before `@Transactional` and `@Version` | Violated 5 of 5 rounds; one round accepted 10 |
| After | Exactly one accepted, 5 of 5 rounds |

Both builds were measured with the identical probe. The pre-fix build was
reconstructed from commit `80b3c9b` and run on a separate port for the comparison,
because an earlier measurement had used a different harness and would not have been
a fair test.

### Runtime upgrade

Latest LTS is Java 25. Establishing that the JDK could not move alone took three
measurements:

| Combination | Result |
|---|---|
| Boot 3.3.2, target 17, run on JDK 25 | Starts — but this is only a newer JVM, not an upgrade |
| Boot 3.3.2, **target 25** | Fails: `Unsupported class file major version 69` at repackage |
| Boot 3.5.16, target 25 | Builds, runs, all checks pass |

Spring Boot 4.0.7 and 4.1.0 exist but bring Spring Framework 7 and breaking changes,
so the upgrade stayed on the 3.x line. Startup time fell from roughly 15-21 seconds
to 7.

## Challenges faced and how they were resolved

### The build silently used the wrong Java

**Problem.** `mvnw` failed with `class file version 61.0 ... only recognizes up to
52.0`. `JAVA_HOME` was not set at all, so the wrapper fell back to `java` on the
`PATH`, which is JDK 8. Only JDK 8 and 11 were installed permanently.

**Resolved.** Installed a JDK to a permanent location and set `JAVA_HOME` at user
scope. `PATH` was deliberately left untouched, so `java` on the command line still
resolves to JDK 8 and anything else on this machine that depends on it keeps working;
the Maven Wrapper reads `JAVA_HOME` in preference.

### A changed environment variable that terminals could not see

**Problem.** After setting `JAVA_HOME`, `echo $env:JAVA_HOME` still printed nothing,
then later printed the old value. This recurred three times.

**Resolved.** A process inherits its environment frozen at start. Inside VS Code, a
new terminal *tab* is still a child of the VS Code process, so the whole editor must
be restarted, not just the terminal. Recorded in `CLAUDE.md`.

### Antivirus deleted the build script and a JDK binary

**Problem.** `backend/mvnw.cmd` disappeared, and every attempt to restore it failed
with `Access denied` even though other files wrote to that folder normally. Later,
`java.exe` vanished from a freshly installed JDK 25 while the other 125 files in
`bin/` survived.

**Resolved.** Avast had quarantined both as false positives. Restored from quarantine
and excluded the project folder and the JDK directory. No attempt was made to work
around or disable the antivirus.

### Spring Boot 3.3.2 could not target Java 25

**Problem.** Setting `<java.version>25</java.version>` failed with
`Unsupported class file major version 69` during repackage, even though compilation
succeeded and the application ran.

**Resolved.** Upgraded Spring Boot to 3.5.16. The failure is in the Maven plugin's
bytecode reader, so it appears only at packaging time — which is why running on JDK
25 without changing the target had looked deceptively fine.

### The editor reported errors the build did not

**Problem.** Two separate cases. TypeScript flagged a missing `rootDir` that
`tsc --noEmit` did not, and the Java extension reported
`release 25 is not found in the system` against a build that succeeded.

**Resolved.** Both were tooling-registry problems rather than code problems. The
editor was using a newer TypeScript than the project, so `typescript.tsdk` now pins
the workspace copy and `rootDir` is explicit. The Java language server keeps a JDK
registry separate from `JAVA_HOME`, so `java.configuration.runtimes` now lists the
installed JDKs with Java 25 as default.

### A reported failure that was not a bug, and one that was

**Problem.** The interface reported "cannot reach the API at http://localhost:8080.
Is the backend running?" while the backend appeared to be running.

**Resolved.** The backend process started earlier had died; the one running at the
time of the report had started afterwards. The application itself was healthy. But
the investigation exposed two real defects:

- The message asserted a single cause. `status 0` means only that no response
  reached the browser, which also happens when CORS refuses the request or a
  security tool intercepts loopback. It now lists the real candidates and points at
  the console.
- CORS allowed `http://localhost:4200` but not `http://127.0.0.1:4200`. Same
  machine, different origin, so the identical page served over one spelling was
  refused with 403 while the other worked — and the browser reports that refusal as
  `status 0`, indistinguishable from the server being switched off. Both spellings
  are now allowed, kept explicit rather than made a wildcard.

## How to run it

```bash
# Terminal 1 — backend (needs JDK 25; Maven not required)
cd "School Management System/backend"
.\mvnw.cmd spring-boot:run          # Linux/macOS: ./mvnw spring-boot:run

# Terminal 2 — frontend
cd "School Management System/frontend/tracker-ui"
npm start
```

Open <http://localhost:4200>. Start the backend first.

To confirm the backend is genuinely up, do not rely on the terminal output — that
was written when it started. Ask it:

```powershell
Invoke-RestMethod http://localhost:8080/api/assignments
```
