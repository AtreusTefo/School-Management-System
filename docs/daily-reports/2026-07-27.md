## What I did today

The goal was simply to run the project. Doing that surfaced a set of real defects,
so the day split into three parts: building a working environment, fixing what the
run exposed, and making the repository self-sufficient so the next person doesn't
have to repeat the setup.

- **Stood up the toolchain.** The machine had JDK 8 and 11 and no Maven; Spring Boot
  3.3.2 requires Java 17+. I used a portable JDK 17 and Maven 3.9.9 from a temporary
  directory rather than changing system settings.
- **Built and launched the backend** on port 8080, then exercised all three endpoints
  directly to see what the API actually returns.
- **Scaffolded the Angular project.** The repository held five hand-written source
  files but no runnable project — no `package.json`, no build config — so `ng serve`
  had nothing to serve.
- **Audited both halves against their error paths**, not just their happy paths. Every
  business-rule failure returned HTTP 500 with an empty body, and the frontend was
  discarding failures silently.
- **Fixed the defects** in the backend web layer and the Angular component, then
  re-verified each one against the running application.
- **Moved the Angular project into the repository** at `frontend/tracker-ui`, added the
  Maven Wrapper, and rewrote the README so each half starts with a single command.

## What was completed

### The application runs end to end

Backend on `localhost:8080`, frontend on `localhost:4200`. Verified in Chrome rather
than by checking ports alone: created an assignment through the form, watched the row
appear, clicked Submit, and watched the status flip to `SUBMITTED`. No console errors.

### Error handling now returns the truth

One missing piece caused four of the defects. The service layer threw exceptions
correctly, but nothing translated them into HTTP status codes, so Spring's fallback
answered 500 — *"the server broke"* — for problems that were really the client asking
for something invalid.

| Situation | Before | After | Message returned |
|---|---|---|---|
| Blank or missing title | 500 | **400** | `title: Title must not be blank` |
| Unknown assignment id | 500 | **404** | `No assignment found with id = 999` |
| Submitting something already sent | 500 | **409** | `Assignment 3 has already been submitted.` |
| Error body content | empty | **JSON** | One consistent shape for every error |

### Everything else that changed

- **Validation is actually switched on.** The `spring-boot-starter-validation`
  dependency was declared in the POM but never used — no `@Valid`, no `@NotBlank`. It
  was dead weight. Both are now in place.
- **Sample data no longer duplicates.** The startup seed ran unconditionally. That is
  harmless against an in-memory database, but pointed at a persistent one it would
  have re-inserted the same two rows on every restart.
- **The UI reports failures.** All three `subscribe()` calls had a success callback and
  nothing else, so a failed request looked exactly like a click that did nothing. There
  is now a dismissible banner that prefers the server's own message and names an
  unreachable backend explicitly.
- **The build no longer needs Maven installed.** Added the Maven Wrapper and confirmed
  a clean build with no Maven on the PATH.

## Challenges faced and how they were resolved

### Antivirus was breaking every HTTPS download

**Problem.** Maven could not reach Maven Central, failing with `PKIX path building
failed`. Avast intercepts HTTPS and re-signs traffic with its own root certificate.
Windows trusts it; a freshly installed JDK does not.

**Resolved.** Read the certificate chain to identify the interceptor, then imported
that root into the portable JDK's truststore only — the system certificate store was
left untouched. npm needed the same certificate via `NODE_EXTRA_CA_CERTS`. Both are now
documented in the README, since anyone on this network will hit it.

### Wrong Java version, and no build tool

**Problem.** Only JDK 8 and 11 were installed, and Maven was absent entirely. Spring
Boot 3.x will not start on either JDK.

**Resolved.** Used a portable JDK 17 and Maven from a temporary directory so nothing
was installed system-wide. To stop this recurring, I added the Maven Wrapper to the
project — the build now fetches its own Maven, leaving a JDK 17 as the only
prerequisite.

### The frontend had no project to run

**Problem.** `frontend/src` contained five source files and nothing else. An Angular app
needs a dozen generated config files before `ng serve` will do anything.

**Resolved.** Scaffolded a real Angular 18 project, copied the five files in, and moved
the result into the repository at `frontend/tracker-ui` with its dependencies
installed. Starting the UI is now `npm start`.

### The browser could not reach a server on its own machine

**Problem.** Command-line requests to `localhost:4200` succeeded, but Chrome hung on the
same URL. The system proxy was capturing loopback traffic too.

**Resolved.** Launched the browser with the proxy bypassed for loopback addresses. A
second, unrelated hang came from waiting on network idle — the dev server's live-reload
socket stays open by design, so that condition never arrives; waiting for the document
instead fixed it.

### Two different failures shared one exception type

**Problem.** The service threw `IllegalArgumentException` for both "the title is blank"
and "no such assignment". Those need different answers — 400 and 404 — but an error
handler cannot distinguish two problems that arrive as the same Java type.

**Resolved.** Gave "not found" its own exception class. Once the two were
distinguishable, mapping each to the right status was straightforward.

### A rebuild failed on a locked file

**Problem.** `clean` could not delete the application jar, because the running backend
still held it open — a detail that only shows up on Windows.

**Resolved.** Stopped the backend before rebuilding. Worth remembering as the normal
edit–build–run rhythm on this machine.

## Open items

- **Two copies of the frontend source.** Moving the Angular project in left
  `frontend/src` and `frontend/tracker-ui/src` holding the same five files. Today's
  fixes went into both and I confirmed they are byte-identical, but nothing keeps them
  in sync. Deleting the originals would settle it — that is the owner's call, so I left
  them in place and documented the risk.
- **Status is a plain string.** `"IN_PROGRESS"` and `"SUBMITTED"` are untyped text,
  which the code's own comments flag. An enum would make invalid states impossible to
  represent. That is a design change rather than a defect fix, so it was left alone.
- **There is no automated test suite.** Today's verification was scripted against the
  running application, which is real evidence but has to be re-run by hand. Committed
  tests would make these guarantees permanent.

## How to run it

```bash
# Terminal 1 — backend (needs JDK 17+; Maven not required)
cd "School Management System/backend"
./mvnw spring-boot:run            # Windows: .\mvnw.cmd spring-boot:run

# Terminal 2 — frontend
cd "School Management System/frontend/tracker-ui"
npm start
```

Open <http://localhost:4200>. Start the backend first so the API is ready.
