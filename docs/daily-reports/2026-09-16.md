### 2. Two tables, with deliberately different integrity postures

A message is written by a person and has an author who can be held to it. A
notification is raised by the system about a record, has no author, and cannot
be replied to. Folding them into one table would have meant a nullable sender,
a nullable subject, and a type column deciding which half of each row was
meaningful - the shape that always ends with rows that satisfy every constraint
and still make no sense. They are separate, and each is fully constrained.

**`notification.subject_type`/`subject_id` deliberately carry no foreign key.**
This is the second and last such deviation in the schema, after
`audit_log.performed_by_id`, and for the same reason: a live reference would
mean that telling a student their mark was posted made that mark undeletable.
A notification must never be the reason a real record cannot be corrected. What
makes it safe is that `title` and `body` are a snapshot written once and never
recomputed, exactly as `audit_log.summary` is.

That is the one place in this system where text is duplicated rather than
derived, and it is worth being explicit that it does not contradict "nothing
derived is stored". A percentage is recomputed because the marks behind it are
still authoritative. A notification records what somebody was **told**, at a
moment; recomputing it would not correct it, it would rewrite what was said.

### 3. The constraint that carries the feature

`uq_notification_recipient_event` — unique on `(recipient_id, dedupe_key)`,
where the key names the **event** rather than the moment: `MARK:41`,
`DUE_SOON:512`, `ABSENCE:903`.

"Tell a student their work is due soon" is produced by a job on a timer. It has
no memory, re-reads the same window every run, and the naive version notifies
the same student about the same assignment every time it wakes. That is the
notification equivalent of taking a register twice and getting two registers,
which V14 already refused to allow.

So `DueDateReminderJob` is written with **no memory at all**. It may run every
fifteen minutes, twice at once after a restart, or having missed a day; a
student is still told exactly once per piece of work, because the guarantee is
in the schema rather than in that job's control flow.

One subtlety this forced: `NotificationService.raise` checks
`existsByRecipientAndDedupeKey` *first*, and that is not a second copy of the
rule. Letting the constraint fire inside a transaction throws
`DataIntegrityViolationException`, and JPA marks the whole transaction
rollback-only when it does — so a duplicate notification would have rolled back
the **mark** that caused it. A student would have lost a recorded score because
the system tried to tell them about it twice. Checking first keeps the ordinary
case away from the constraint; the constraint still settles a genuine race,
where losing that one transaction and retrying is correct.

### 4. Who may write to whom

A school is not a social network, so this is a safeguarding rule rather than a
UI preference:

- an admin may write to anybody
- a teacher to their own students, any other teacher, and any admin
- a student to the teachers who actually teach them, and any admin —
  **never to another student**

None of it is expressible as a `CHECK`: every clause reads `Course` or
`Enrolment`. So it joins the short, explicitly-listed set of rules this system
enforces in Java alone, alongside the three attendance rules and
no-overlapping-terms. Everything the database *can* enforce about a message, it
does: both ends are real accounts with roles pinned by composite foreign keys,
nobody writes to themselves, the body is not blank, and a read time cannot
precede the send.

The compose form is built from the **same predicate** that refuses a send,
rather than a parallel query. Two implementations would drift, and the visible
symptom would be a form offering somebody the send path then rejects — or
worse, hiding somebody a student is entitled to reach.

### 5. Deletion

Messages and notifications are the "current arrangement" side of this system's
oldest distinction, so `deleteStudent`/`deleteTeacher` clear them with the
account, the way enrolments and reset tokens already are — rather than refusing
the delete the way a mark, a submission or a register does. Never a cascade;
the database stays `NO_ACTION` throughout and the service makes the decision
explicitly. This does remove the other party's copy of a conversation, which is
stated plainly in the privacy policy rather than left to be discovered.

## Challenges faced and how they were resolved

### A transaction that would have destroyed a mark

Writing the duplicate-notification guard, the obvious implementation was to let
the unique constraint do the work and catch the violation. That is wrong here,
and the reason is not obvious until you know it: JPA marks a transaction
rollback-only when a constraint fires inside it, so a mark and the notification
about it — deliberately in one transaction, so a rolled-back mark cannot leave
a notification claiming it was posted — would both have been lost because the
student was nearly told twice.

Resolved by checking first and leaving the constraint as the backstop for a
genuine race, and by writing down *why* both exist, because the next reader
will otherwise see a redundant check and delete one of them.

### My own tests failing for four different fixture reasons

The first run of the new suites failed 13 tests, none of them because the
feature was wrong:

- `POST /api/assessments` answers **200**, not 201 — it carries no
  `@ResponseStatus`.
- the register lives at `/api/attendance/lessons/{slotId}`, not
  `/api/attendance/{slotId}`.
- `/api/accounts` is a **front-end** route; the API lists each role separately
  at `/api/admins`.
- creating a person requires `phone` and `temporaryPassword`, and names are
  validated against a letters-only pattern — so appending a counter to a
  surname to make fixtures unique is a 400. Uniqueness has to come from the
  Omang, which is the uniquely-constrained column.

Each was found by reading the actual response rather than guessing, and the
last one is worth keeping: the canonical payload already existed in
`AdminApiTest.personJson`, and copying it would have avoided all of it.

### A badge that never appeared

Browser-verified, and the suite caught a real defect immediately: after signing
in, the unread badges were empty until the user clicked something.

The cause was that the badges refreshed on `NavigationEnd`, and signing in
while already on `/` navigates to `/` — the same URL — for which the Router
emits no `NavigationEnd` at all. No unit test would have shown this; the gap is
in the Router's behaviour, not in anything the component computes.

The first fix made it worse in a quieter way. An `effect()` over
`session.user()` did fire at the right moment, but writing a signal inside an
effect is disallowed by default, so it traded a missing badge for a console
error on every sign-in. Replaced with explicit refreshes at the three points
where the session actually changes — `init()` settling, a successful login, and
each navigation — which is both correct and more in keeping with a codebase
that has twice been bitten by depending on an asynchronous value having arrived.

### A nav that rendered underneath the new icons

The worst-looking defect of the day, and the one that had to be *seen*. Adding
two icons to the right-hand end of the app bar pushed a teacher's navigation
past the bar's 1320px cap, and because `.appbar__end` could shrink while
`.nav__link` is `nowrap`, the links overflowed their own box and ran
**underneath** the envelope: "Performance & marks" was half-hidden behind an
icon.

Every existing assertion passed while that was on screen. The bar was not
wrapping (one row of links) and the page was not overflowing horizontally,
because the overflow was inside the nav rather than the document. Not wrapping
is not the same as fitting.

Resolved in three parts, measured rather than guessed: `.appbar__end` no longer
shrinks; the bar's cap went to 1400px; and the single longest nav label became
"Marks", which bought back more width than the two icons cost — so laptops keep
the worded navigation instead of being pushed into the hamburger. The hamburger
panel and the dashboard quick-link keep the fuller wording, because neither is
short of room. A probe then confirmed no clipping at any width from 1900px down
to 1280px, where the hamburger correctly takes over.

`nav.mjs` now asserts the nav does not collide with the app-bar icons, which is
the assertion that was missing. It reports 16px of clearance.

### Two documentation pages that were about to become wrong

Two weeks ago the landing and about pages were corrected for saying the system
had no attendance register and no timetable, long after both shipped. Both then
said, accurately, that there was no messaging and no notifications — which this
feature made false the moment it merged.

That did not slip through, because the deny-list in `public-copy.mjs` written
during that same correction failed immediately on the new copy. The pages now
say what is *still* genuinely absent — nothing leaves the building: no email,
no SMS, no push, and nobody is texted when a child is marked absent — and the
deny-list grew to cover the claims that just stopped being true.
