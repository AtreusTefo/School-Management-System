## What I did today

### 1. The four diagnostics

All four were real, not stale index noise, and all four had the same shape the
project has already written down how to handle.

- **An unused `SchoolClass` import in `AttendanceRepository`.** Left behind
  when the dead finder above it was removed a fortnight ago - the method went,
  the import stayed. The comment explaining the removal now says the import
  went too, so nobody re-adds one to satisfy a dangling reference.
- **Three null-safety warnings** in the new code, each a method reference
  passed through an unannotated JDK generic: `Long::sum` through `Map.merge`'s
  `BiFunction`, `PersonProfile::getFullName` through `Optional.map`'s
  `Function`, and `Notification::markRead` through `List.forEach`'s `Consumer`.

None was suppressed. Each became an explicit local or an ordinary loop, which
is what Eclipse's flow analysis verifies natively with nothing annotated - the
same technique `Require.orThrow` exists for, and the one CLAUDE.md's
Nullability section prescribes. `@SuppressWarnings("null")` remains test-only.

### 2. Two tables, with deliberately different integrity postures

A message is written by a person and has an author who can be held to it. A
notification is raised by the system about a record, has no author, and cannot
be replied to. Folding them into one table would have meant a nullable sender,
a nullable subject, and a type column deciding which half of each row was
meaningful - the shape that always ends with rows that satisfy every constraint
and still make no sense. They are separate, and each is fully constrained.

**`notification.subject_type`/`subject_id` deliberately carry no foreign key.**
This is the second and last such deviation in the schema, after
`audit_log.performed_by_id`, and for the same reason: a live reference would
mean that telling a student their mark was posted made that mark undeletable.
A notification must never be the reason a real record cannot be corrected. What
makes it safe is that `title` and `body` are a snapshot written once and never
recomputed, exactly as `audit_log.summary` is.

That is the one place in this system where text is duplicated rather than
derived, and it is worth being explicit that it does not contradict "nothing
derived is stored". A percentage is recomputed because the marks behind it are
still authoritative. A notification records what somebody was **told**, at a
moment; recomputing it would not correct it, it would rewrite what was said.

### 3. The constraint that carries the feature

`uq_notification_recipient_event` — unique on `(recipient_id, dedupe_key)`,
where the key names the **event** rather than the moment: `MARK:41`,
`DUE_SOON:512`, `ABSENCE:903`.

"Tell a student their work is due soon" is produced by a job on a timer. It has
no memory, re-reads the same window every run, and the naive version notifies
the same student about the same assignment every time it wakes. That is the
notification equivalent of taking a register twice and getting two registers,
which V14 already refused to allow.

So `DueDateReminderJob` is written with **no memory at all**. It may run every
fifteen minutes, twice at once after a restart, or having missed a day; a
student is still told exactly once per piece of work, because the guarantee is
in the schema rather than in that job's control flow.

One subtlety this forced: `NotificationService.raise` checks
`existsByRecipientAndDedupeKey` *first*, and that is not a second copy of the
rule. Letting the constraint fire inside a transaction throws
`DataIntegrityViolationException`, and JPA marks the whole transaction
rollback-only when it does — so a duplicate notification would have rolled back
the **mark** that caused it. A student would have lost a recorded score because
the system tried to tell them about it twice. Checking first keeps the ordinary
case away from the constraint; the constraint still settles a genuine race,
where losing that one transaction and retrying is correct.

### 4. Who may write to whom

A school is not a social network, so this is a safeguarding rule rather than a
UI preference:

- an admin may write to anybody
- a teacher to their own students, any other teacher, and any admin
- a student to the teachers who actually teach them, and any admin —
  **never to another student**

None of it is expressible as a `CHECK`: every clause reads `Course` or
`Enrolment`. So it joins the short, explicitly-listed set of rules this system
enforces in Java alone, alongside the three attendance rules and
no-overlapping-terms. Everything the database *can* enforce about a message, it
does: both ends are real accounts with roles pinned by composite foreign keys,
nobody writes to themselves, the body is not blank, and a read time cannot
precede the send.

The compose form is built from the **same predicate** that refuses a send,
rather than a parallel query. Two implementations would drift, and the visible
symptom would be a form offering somebody the send path then rejects — or
worse, hiding somebody a student is entitled to reach.

### 5. Deletion

Messages and notifications are the "current arrangement" side of this system's
oldest distinction, so `deleteStudent`/`deleteTeacher` clear them with the
account, the way enrolments and reset tokens already are — rather than refusing
the delete the way a mark, a submission or a register does. Never a cascade;
the database stays `NO_ACTION` throughout and the service makes the decision
explicitly. This does remove the other party's copy of a conversation, which is
stated plainly in the privacy policy rather than left to be discovered.

## Challenges faced and how they were resolved

### A transaction that would have destroyed a mark

Writing the duplicate-notification guard, the obvious implementation was to let
the unique constraint do the work and catch the violation. That is wrong here,
and the reason is not obvious until you know it: JPA marks a transaction
rollback-only when a constraint fires inside it, so a mark and the notification
about it — deliberately in one transaction, so a rolled-back mark cannot leave
a notification claiming it was posted — would both have been lost because the
student was nearly told twice.

Resolved by checking first and leaving the constraint as the backstop for a
genuine race, and by writing down *why* both exist, because the next reader
will otherwise see a redundant check and delete one of them.

### My own tests failing for four different fixture reasons

The first run of the new suites failed 13 tests, none of them because the
feature was wrong:

- `POST /api/assessments` answers **200**, not 201 — it carries no
  `@ResponseStatus`.
- the register lives at `/api/attendance/lessons/{slotId}`, not
  `/api/attendance/{slotId}`.
- `/api/accounts` is a **front-end** route; the API lists each role separately
  at `/api/admins`.
- creating a person requires `phone` and `temporaryPassword`, and names are
  validated against a letters-only pattern — so appending a counter to a
  surname to make fixtures unique is a 400. Uniqueness has to come from the
  Omang, which is the uniquely-constrained column.

Each was found by reading the actual response rather than guessing, and the
last one is worth keeping: the canonical payload already existed in
`AdminApiTest.personJson`, and copying it would have avoided all of it.

### A badge that never appeared

Browser-verified, and the suite caught a real defect immediately: after signing
in, the unread badges were empty until the user clicked something.

The cause was that the badges refreshed on `NavigationEnd`, and signing in
while already on `/` navigates to `/` — the same URL — for which the Router
emits no `NavigationEnd` at all. No unit test would have shown this; the gap is
in the Router's behaviour, not in anything the component computes.

The first fix made it worse in a quieter way. An `effect()` over
`session.user()` did fire at the right moment, but writing a signal inside an
effect is disallowed by default, so it traded a missing badge for a console
error on every sign-in. Replaced with explicit refreshes at the three points
where the session actually changes — `init()` settling, a successful login, and
each navigation — which is both correct and more in keeping with a codebase
that has twice been bitten by depending on an asynchronous value having arrived.

### A nav that rendered underneath the new icons

The worst-looking defect of the day, and the one that had to be *seen*. Adding
two icons to the right-hand end of the app bar pushed a teacher's navigation
past the bar's 1320px cap, and because `.appbar__end` could shrink while
`.nav__link` is `nowrap`, the links overflowed their own box and ran
**underneath** the envelope: "Performance & marks" was half-hidden behind an
icon.

Every existing assertion passed while that was on screen. The bar was not
wrapping (one row of links) and the page was not overflowing horizontally,
because the overflow was inside the nav rather than the document. Not wrapping
is not the same as fitting.

Resolved in three parts, measured rather than guessed: `.appbar__end` no longer
shrinks; the bar's cap went to 1400px; and the single longest nav label became
"Marks", which bought back more width than the two icons cost — so laptops keep
the worded navigation instead of being pushed into the hamburger. The hamburger
panel and the dashboard quick-link keep the fuller wording, because neither is
short of room. A probe then confirmed no clipping at any width from 1900px down
to 1280px, where the hamburger correctly takes over.

`nav.mjs` now asserts the nav does not collide with the app-bar icons, which is
the assertion that was missing. It reports 16px of clearance.

### Two documentation pages that were about to become wrong

Two weeks ago the landing and about pages were corrected for saying the system
had no attendance register and no timetable, long after both shipped. Both then
said, accurately, that there was no messaging and no notifications — which this
feature made false the moment it merged.

That did not slip through, because the deny-list in `public-copy.mjs` written
during that same correction failed immediately on the new copy. The pages now
say what is *still* genuinely absent — nothing leaves the building: no email,
no SMS, no push, and nobody is texted when a child is marked absent — and the
deny-list grew to cover the claims that just stopped being true.

## What I did today

The day's second half started with a question rather than a request: **is this
web app complete and ready for production?** The answer was no, and the useful
part of answering was doing it from evidence rather than impression — reading
the configuration, grepping for the protections that were assumed to exist, and
starting the application in the states a deployment would actually be in.

That produced a list of blockers, and the rest of the day was spent closing
them. Three pieces of work came out of it.

### 1. A production profile that refuses to start half-configured

`application.properties` was the only configuration file in the project, and it
is the development one. Every value a deployment must change had a development
default sitting behind it: the database URL, the password, the allowed CORS
origin, and `app.openapi.enabled=true`.

`application-prod.properties` now sits beside it and **removes** those defaults
rather than replacing them. Every secret is written as a bare `${DB_URL}`-style
placeholder with no `:default` suffix, so an unset variable cannot quietly
resolve to the development one. It also turns Swagger off, marks cookies
`Secure` with a configurable `SameSite`, honours `X-Forwarded-*`, disables
`baseline-on-migrate`, and keeps SQL and bind parameters out of the log —
bind parameters include Omang numbers, contact emails and dates of birth, and a
log is a far easier thing to read than the database it describes.

**The seed accounts are gated in Java, not in a properties file**, because a
properties file cannot disable a bean. All four `CommandLineRunner` beans in
`TrackerApplication` now carry `@Profile("!prod")`. The exclusion is deliberate
and is not the same as `@Profile("dev")`: the test profile has Flyway switched
off, so those runners are the only thing that creates the accounts, courses and
classes that `AttendanceApiTest`, `MessagingApiTest`, `NotificationApiTest` and
the rest are written against. `@Profile("dev")` would have switched the suite
off along with production, and the failure would have looked like a broken
feature rather than a missing fixture.

### 2. Brute-force protection on sign-in

`POST /api/auth/login` could be called as fast as the network allowed. BCrypt at
cost 10 is real protection against an offline crack of a stolen hash; it is not
protection against an attacker who simply keeps asking. Nothing counted, so
nothing ever said no.

V19 adds `login_attempt`, which records **failed** attempts only. Failures are
counted per username and per source address over a sliding window; past either
limit the endpoint answers **429 without looking at the password**. Four things
about the design are load-bearing:

- **Nothing is locked.** There is no flag on `AppUser`, nothing an
  administrator has to undo, and no state that outlives the window. Whether
  sign-in is refused is computed by counting rows, the same rule percentages
  and performance levels already follow. This is not tidiness. A username-keyed
  limit is unavoidably a way to make *somebody else* fail to sign in — anybody
  who knows a student's id can spend ten guesses on it — and a persistent lock
  would turn that into a denial of service with an administrator in the loop to
  reverse it, once per victim. A sliding window bounds the damage at the
  window's length and needs nobody.

- **A failure is counted for ANY attempted username, real or invented.** This
  is what stops the throttle becoming an account-enumeration oracle. 429 has to
  be as easy to reach with a made-up id as with a real one, or the difference
  between 429 and 401 becomes a reliable test for which sign-in ids exist —
  undoing from a new direction exactly what `PasswordResetService` is built to
  prevent. It is also why `login_attempt` has no foreign key to `app_user`: the
  third and last such omission in this schema, and the only one where the
  missing key is a security property rather than a deletion convenience.

- **The failure is written in its own `REQUIRES_NEW` transaction.** It is
  recorded as a sign-in is about to end in a 401, and it has to commit anyway.
  A failure that rolled back with the request it belongs to would leave the
  counter permanently at zero and the throttle permanently off — a defect that
  only shows up on the day it is needed.

- **The per-IP limit is the loose one, deliberately.** A school is the NAT case:
  a whole computer lab reaches the server from one public address, so a limit
  tight enough to stop a determined sprayer would lock out a classroom on a
  Monday morning. Per-IP catches the careless; per-username is the rule that
  actually holds.

The 429 also had to reach the person being refused. It now renders inline on
the sign-in form, next to where they are looking, rather than in the page-level
error banner — and it uses the **server's** sentence rather than one written in
the client, because that sentence is deliberately vague about which limit was
reached and how long remains, and a second copy would be free to become more
specific, and more useful to somebody guessing, without anyone noticing.

### 3. Reset links that can no longer reach the log unnoticed

`ResetLinkMailer` sends real email when `spring.mail.host` is set and writes the
link to the log at WARN when it is not. That fallback is right for development
and announces itself on every send. In production it means anybody who can read
the application log can take over any account by following a link they find
there — and because the fallback never throws, nothing else goes wrong to make
it noticeable.

`MAIL_HOST` and `RESET_LINK_BASE` are now required by the prod profile, which
turns a quiet condition into a refusal to start. `RESET_LINK_BASE` matters for
its own reason: its default is `http://localhost:4200/reset-password`, so a
deployment that forgets it sends out reset emails that only work on the server
that sent them.

A health check went in alongside: `/actuator/health`, the single exposed
actuator endpoint and the one path that does not require a session, because a
load balancer cannot sign in. `show-details=never`, so it answers `UP` or `DOWN`
without describing the infrastructure behind it to an anonymous prober.

## Challenges faced and how they were resolved

### A check that ran too late to say anything

`ProductionConfigCheck` began as a static `@Bean BeanFactoryPostProcessor`,
which is early enough to beat the DataSource and Flyway, and that was verified:
starting the prod profile with nothing configured named all four variables in
one message.

Adding `MAIL_HOST` broke it immediately. `MailSenderAutoConfiguration` carries a
condition on `spring.mail.host`, and conditions are evaluated by
`ConfigurationClassPostProcessor` — itself a `BeanFactoryPostProcessor`, which
runs first. The result was a placeholder error about `MAIL_HOST` alone, and the
other five missing variables were never mentioned.

Resolved by moving it to an `EnvironmentPostProcessor` registered in
`META-INF/spring.factories`, ordered `LOWEST_PRECEDENCE` so it runs after
`ConfigDataEnvironmentPostProcessor` has loaded the profile's properties and
settled the active profiles. It now runs before any configuration class is
parsed and before any condition is evaluated, so there is nothing left that can
get in first. Registered in `spring.factories` rather than annotated, because a
class Spring instantiates this early cannot be found by component scanning —
scanning has not happened yet, and is one of the things being protected.

### Two halves of Spring disagreeing about an unresolved placeholder

The bare-placeholder approach rests on an assumption worth having measured
rather than believed: that an unset variable makes startup fail. It does, but
not uniformly.

A property read through `@Value` throws `PlaceholderResolutionException` naming
the variable. A property bound through `@ConfigurationProperties` — every
`spring.datasource.*` value, via Boot's `Binder` — resolves placeholders with
`ignoreUnresolvablePlaceholders = true` and passes an unset one along **as the
literal text** `${DB_URL}`. The deployment still fails, so the security property
holds, but it fails as `Driver ... claims to not accept jdbcUrl, ${DB_URL}`
forty lines into a Hikari stack trace. An unset `DB_PASSWORD` is worse: the
password becomes the literal text and SQL Server answers with an ordinary login
failure, which reads exactly like a wrong password and sends whoever is
deploying to look at the database instead of at their environment.

This is the reason `ProductionConfigCheck` exists at all, and the division is
the project's usual one applied to configuration rather than to data: the
placeholders are the guarantee, and the check is the message.

### A verification I was not allowed to run

Proving the seed gate properly meant writing a junk password hash into the
development database, starting the prod profile, and confirming it was left
alone. That write was refused — reasonably, since tampering with a stored
credential is not something to wave through — and I did not work around it.

"No seed log lines appeared" was the fallback, and it is weak evidence on its
own: `ensureAccount` only logs when it *changes* something, and the accounts
already matched, so it would have logged nothing either way.

The better answer turned out to be permanent rather than one-off. Instead of a
manual check somebody would have to remember to repeat, the invariant became
`ProductionProfileTest`, which reflects over `TrackerApplication` and fails the
build if any seed runner is ungated. A new `@Bean CommandLineRunner` looks
exactly like the four already there, which is precisely the kind of mistake that
survives review — so a test is the right place for it regardless of whether the
manual check had been possible.

### A test that failed on its own assertion, not on the code

`theMessageLeaksNothing` asserted that the 429 body contained no digit, on the
grounds that an attempt count, a remaining count or a window length would each
have to be written as one. It failed. The body was clean; the ISO timestamp in
the error envelope contains a `3`.

Rewritten to assert against the `message` field rather than the whole envelope,
and — more usefully — a second test now compares the refusal a real username
receives with the refusal an invented one receives and requires them to be
identical. That tests the property that actually matters and cannot trip over
the parts of the body that are the same either way.

### A throttle that could throttle its own test suite

Every MockMvc request in the suite arrives from the same loopback address, so
all the deliberately-failed sign-ins in `AssignmentApiTest`,
`InputValidationApiTest`, `PasswordResetApiTest` and the rest land in one
per-IP bucket. At the production default of 60 the suite would eventually
throttle itself, and the failure would have looked like a broken endpoint rather
than one test interfering with another — the shared-mutable-state shape this
project has already been bitten by twice.

Resolved by **raising** the limits in `application-test.properties` rather than
switching the feature off, so the code path still runs on every sign-in in the
suite, and giving `LoginThrottleTest` its own small limits with
`@TestPropertySource`. That test therefore depends on neither number, and gets
its own application context and H2 database as a side effect, which is the right
isolation for a class whose subject is accumulated state.

### A requirement I introduced that the deployment shape does not need

Flagged against my own work while writing the readiness assessment:
`ProductionConfigCheck` demands `APP_CORS_ALLOWED_ORIGINS`, but the production
frontend build uses `apiBaseUrl: ''` — relative URLs — so the intended
single-origin deployment behind a reverse proxy needs no CORS at all. I was
forcing an operator to set a value that does nothing in the normal topology.

Resolved as documentation rather than code, after checking what removing it
would actually do. `CorsConfig` reads the property with `@Value` and no default,
so dropping it from the prod file would mean **inheriting
`http://localhost:4200` from the shared file** and granting it credentialed
access to a production API. Keeping it required and explaining what to put —
the site's own origin — is the better of the two.

### Two defects in a probe script, neither of them today's code

`timetable.mjs` failed with a twenty-second `TimeoutError` waiting for
`#loginUsername`. Its `signOut()` was the naive version — look for a visible
"Sign out" button, and return **quietly** if there is none — which is exactly
the defect already fixed in `relations.mjs` and `messaging.mjs` during the first
half of the day, when the app bar gained two icons and started collapsing that
button behind the hamburger. The previous account was still signed in, so the
login form the next step waited for was never going to appear.

Fixing that revealed a second, older piece of drift: the script called
`page.fill()` on `#courseTeacher`, which has since become a `<select>`. Both
were repaired in the scratchpad script, which now reports 16/16.

Neither was caused by today's changes — the only frontend change was one `else
if` branch in a login error handler, which cannot affect whether a button
renders — but both are worth recording, because a probe that aborts looks
identical to a probe that found a real defect until somebody reads the stack
trace.
