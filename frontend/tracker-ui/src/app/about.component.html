About

Built to replace remembering with a record.

Assignment Tracker started from a problem every teacher recognises: the work has been set, some of it has been handed in, and the only place that fully exists is in somebody's head, a spreadsheet, and a pile of paper that disagree with each other.

The answer here is deliberately bounded. A timetable, a register, and one shared list of assignments with their submission state and marks - each held to rules the database itself enforces, rather than a broad system that tracks everything loosely.

What it is

Assignment Tracker is a full-stack web application for tracking assignment submission state in a school. A teacher sets one piece of work against a course, and it becomes a submission for every student enrolled in that class. Students hand in a PDF. Teachers mark what arrives, and the marks roll up into per-subject percentages and performance levels that are calculated fresh every time they are read.

Around that sits the school week itself. An administrator defines the terms and the periods a day is divided into, and places each course in a period on a weekday - so "timetable" here means both who teaches what to whom and when it happens. Attendance is then taken against a lesson on a date rather than once a day, which is the only way to record a student who was present at first period and missing by fourth.

People can also write to each other, within limits the system enforces rather than merely suggests: a student may message the teachers who actually teach them and the office, and nobody else. Alongside that, the system raises a notice of its own when a mark is posted, when a register marks somebody absent, and when work is nearly due - each one tied to the event that caused it, so the same thing cannot be announced twice.

The administration it needs to be usable sits around that in turn: an administrator onboards accounts one at a time or in bulk, maintains the subjects, classes and courses that define who is taught what by whom, can see from either end what a teacher teaches and which teachers reach a given student, and can review an audit log of every change the system has made.

How it is built

A Spring Boot REST API in Java backs an Angular single-page interface, with SQL Server holding the data. The two halves are deployed separately and share nothing but the API contract between them.

The schema is managed by versioned migrations, and the application is never permitted to alter it at runtime - a mismatch between what the code expects and what the database holds stops the application at startup rather than surfacing later as corrupt data. An automated test suite covers the business rules, the error contract, concurrency, and the constraints themselves.

Deliberate limits

This system covers teaching, work, marks, attendance, messaging and notices. What it deliberately does not do is leave the building: every message and every notification arrives on a page inside this app, and there is no email, no SMS and no push notification behind any of it. Nobody is texted when a child is marked absent. It holds no fees, no library, no behaviour records, and produces no school report beyond the marks it was given. Those are real needs, and they are not what this was built for; pretending otherwise would only move the confusion somewhere less visible.
